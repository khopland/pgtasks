# Schema benchmark: queue + task against a single table

Run on 2026-11-20 with `task2-benchmark` (commit 8fb1597 plus the dependency update in
642b58e). It compares the Task 2.0 schema (a small `tasks.queue` for unfinished tasks, history in
`tasks.task`, partitioned by topic) with a single-table design that keeps unfinished and finished
tasks in one partitioned table, with the same indexes, made partial where that helps.

> **Since then:** `tasks.task` is no longer partitioned (one table, primary key `id`), and the
> benchmark's single table isn't either. A rerun at 0 and 1 million history rows gave the same
> results within the noise described under [Caveats](#caveats); for example, the queue design's
> SINGULAR at 1 million rows ran at 103,584 tasks a second and its idle poll took 0.18 ms.

## Short answer

- **Neither design slows down as history grows.** From 0 to 25 million finished tasks in the
  topic, an idle poll costs 0.18 to 0.22 ms and claims keep their latency in both designs.
- **Both collapsed at first, for the same reason, and both are fixed.** At 1 million history
  rows the per-identifier ordering (SINGULAR) fell to 319 (queue) and 130 (single table) tasks a
  second on the VM, and to 386 for the single table on this machine. That was claim planning
  on statistics that said there were no unfinished tasks, not the schema. See
  [What went wrong at 1 million rows](#what-went-wrong-at-1-million-rows).
- **In these bursts the single table is not slower.** It completes a batch with one update
  instead of a delete plus an update, and its SINGULAR runs were faster. The queue design's case
  rests on what a 20,000-task burst after `VACUUM ANALYZE` doesn't show: a hot table that stays
  small under sustained load, no index writes on a 25-million-row table for every claim, and
  autovacuum that only has to keep a small table clean. A sustained-load run is needed to
  measure that (see [Caveats](#caveats)).

## Workload

- **History**: finished tasks in the topic, over 200,000 identifiers, created one second apart
  and inserted in bulk, then `VACUUM ANALYZE`.
- **Scenarios**: 20,000 ready tasks for 5,000 identifiers (4 each), drained by 4 workers that
  claim batches of 100 and complete each batch in its own transaction. All scenarios run one
  after another on the same database, so later ones see the earlier ones' churn.
  - *idle poll*: 1,000 claims against an empty queue.
  - *FIFO*: no ordering.
  - *SINGULAR*: per-identifier ordering, statistics taken with the tasks queued.
  - *SINGULAR after analyzing an empty queue*: statistics taken right after the previous
    scenario drained, which is what autovacuum usually sees on a queue.
  - *ON_FAILURE, 100k dead letters*: per-identifier ordering behind 100,000 dead letters.
  - *one hot identifier*: 2,000 tasks for one identifier. Only one can run at a time, so
    this measures a claim and completion round trip, not the schema.
  - *FIFO with strict admission*: claims also lock and charge a token bucket row (queue
    design only; it is a store feature).

## What went wrong at 1 million rows

The first runs (on the VM, and for the single table on this machine) collapsed in the SINGULAR
scenario at 1 million history rows: 319 tasks a second with a claim p99 of 3.1 s for the queue
design, 130 and later 386 for the single table. Separating claim from completion latency,
sampling `pg_stat_activity` and logging plans with auto_explain showed:

1. **Statistics without unfinished tasks.** For the single table, the `ANALYZE` after the
   history load saw only finished tasks, so the partial index on unfinished tasks looked empty,
   and 1 million rows need 100,000 changes before autoanalyze runs again. For the queue it was
   autovacuum analyzing `tasks.queue` right after the FIFO scenario drained it, which depends on
   timing. That is why the VM saw it and this machine at first did not.
2. **Every plan looks free.** Expecting one row, the planner made the per-identifier check a
   nested-loop anti-join whose inner scan used only `topic_id`, so each candidate read every
   unfinished task of the topic: 7.2 million buffer hits and 1.9 s for one claim of 100 tasks.
3. **Locks held by slow claims stall completions.** A claim that rechecks a row another worker
   just claimed keeps that row locked until it commits, so completions waited on
   `Lock:transactionid` behind the slow claims.

The fix (commit 84882ac) makes claims plan the same way whatever the statistics say. It's
covered by `ClaimPlanTest`, which drains 20,000 tasks for 5,000 identifiers after analyzing an
empty queue: about 30 s per ordering before, 1.6 to 2.7 s after.

- The identifier check is a subplan per candidate (`OFFSET 0`), so the identifier is always a
  condition of the index lookup. Its state test is a `CASE`, because with an `OR` the planner
  added a bitmap arm that scanned every active task once per candidate (5 times slower even
  with fresh statistics).
- `queue_dedup_idx` is partial (schema version 3). As a full index led by `topic_id` it tied
  with the identifier index, and the planner took it.
- Rows a claim selected and locked are updated by `ctid`, not through a join that was driven
  from a full scan of the queue.
- A claim pins its plan with transaction-local planner settings. With empty statistics the
  planner otherwise switched to a bitmap scan of the whole topic plus a sort, checking every
  ready task's identifier on every claim.

The single-table design in the benchmark gets the same treatment, so the comparison stays fair.

## Caveats

- **Durability is off.** With `fsync`, `synchronous_commit` and `full_page_writes` off, commits
  cost almost nothing, so these numbers are upper bounds for CPU and locking. On a real server
  every completion waits for a WAL flush, which narrows the differences between designs and
  scenarios.
- **Short, noisy scenarios.** 20,000 tasks drain in 0.15 to 0.3 s. Repeated runs of the same
  scenario differ by up to 30 %; for example, single-table SINGULAR at 0 history reached
  111,610 tasks a second in one run and 85,931 in this one. Differences smaller than that are
  noise.
- **Bursts, not sustained load.** Every scenario starts right after setup, which ends in
  `VACUUM ANALYZE` of history that was bulk-loaded in order. What the queue design is for
  doesn't show in that: a hot table that stays small while autovacuum keeps up, and no index
  writes on the large table for every claim and retry. Measuring it needs a run of an hour or
  more with continuous pushes and claims, at 25 million history rows, comparing throughput
  over time, table and index bloat, and autovacuum activity.
- **One topic, one machine.** Client and server share the machine. Several topics in one
  queue table, and a separate database host, are not covered.
- **One identifier at a time.** The hot-identifier scenario is bound by one claim and one
  completion per task, about 300 a second here. Both designs behave the same there.

## Reproducing

```
mvn -Pbenchmark -pl task2-benchmark -am install -DskipTests
mvn -Pbenchmark -pl task2-benchmark test -Dbenchmark.history=0,1000000,10000000,25000000
```

The report goes to `task2-benchmark/target/benchmark-results.md`. Add
`-Dbenchmark.diagnose=true` (with `-Dbenchmark.explain-over=5ms` and `-Dbenchmark.scenarios=...`)
to sample wait events and log plans to `task2-benchmark/target/postgres-logs`. Diagnosis slows
the run, so its numbers aren't comparable with these.
